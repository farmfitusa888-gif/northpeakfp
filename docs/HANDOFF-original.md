## 4. How the site is built

**Stack:** plain HTML/CSS/JS. No framework, no build step, no dependencies at
runtime. ~20KB of CSS, one small JS file. It is deliberately simple and fast.

**But the HTML is generated.** Five Python scripts produce all 32 pages. Editing
`about.html` directly works until someone re-runs the build, then it's gone.

### Generator scripts (in `generators/`)

| Script | Produces | Run order |
|---|---|---|
| `generate_articles_northpeak.py` | Not run directly — it's the **data module**. Holds the CLIENT CONFIG block and the `ARTICLES` list (all 25 articles' text). Imported by the others. | — |
| `build_site.py` | `assets/style.css`, `assets/app.js`, favicon. Also defines the `shell()` function every page uses (nav, footer, meta tags). | 1st |
| `build_pages.py` | `index.html` (homepage) | 2nd |
| `build_pages2.py` | `services.html`, `about.html`, `articles/index.html`, `resources.html`, `contact.html`, `404.html`, `robots.txt`, `sitemap.xml` | 3rd |
| `build_articles_shell.py` | All 25 article pages | 4th |
| `mk_photos.py` | Headshot crops + `og-image.jpg`. Needs the original photo. | 5th |
| `make_guides.py` | The two PDF guides. Independent of the site. | any |

**Requirements:** `pip install reportlab pillow` (plus `beautifulsoup4` if you use
the validation script in §6).

**Output path:** controlled by `ROOT` in `build_site.py`. Change it to wherever you
want the site written.

### Where to change what

| Change | File | Where in it |
|---|---|---|
| Firm name, phone, email, city, founder | `generate_articles_northpeak.py` | CLIENT CONFIG block at top |
| Article text, add/remove articles | `generate_articles_northpeak.py` | `ARTICLES` list |
| SEO title override (for titles >60 chars) | `generate_articles_northpeak.py` | `SEO_TITLES` dict |
| Colors, fonts, all styling | `build_site.py` | the `CSS` string |
| Nav, footer, every page's meta tags | `build_site.py` | the `shell()` function |
| Homepage content | `build_pages.py` | |
| Services / About / Contact / Resources | `build_pages2.py` | |

| Article page layout | `build_articles_shell.py` | |
| Photo crops, og-image | `mk_photos.py` | |

### Adding an article

1. Copy an entry in the `ARTICLES` list in `generate_articles_northpeak.py`.
2. Change `slug`, `cat`, `title`, `desc`, `keywords`, `read`, `lede`, `sections`.
3. If the title exceeds 60 characters, add a short version to `SEO_TITLES`.
4. Re-run `build_pages2.py` (updates the hub and sitemap) and `build_articles_shell.py`.

Internal links, the related-articles block, the sitemap, and the articles hub all
update automatically.

## 7. THE ACTIVE PROBLEM — Search Console indexing errors

**Honesty first: I have not seen the actual Search Console report.** The user says
there are "too many errors." The site went live ~August 1 and it is now mid-August,
so ~2+ weeks have passed — that is long enough that errors are real signal, not just
crawl delay. Below are ranked hypotheses. **Verify against the actual GSC "Pages"
report before changing anything.**

### Hypothesis 1 — duplicate URLs (very likely the bulk of it)

**Every page is reachable at two URLs, both returning 200.**

```
https://northpeakfp.com/services        200  ← canonical, in sitemap
https://northpeakfp.com/services.html   200  ← same content, no redirect
```

This happens because `_redirects` uses **200 rewrites** for clean URLs while the
`.html` files still exist and are served directly. 31 pages × 2 forms = up to 62
discoverable URLs for 31 real pages.

Search Console reports these as *"Alternate page with proper canonical tag"* or
*"Duplicate without user-selected canonical."* They appear under **Not indexed**,
which reads as a wall of errors even though the canonical is doing its job.

**Fix:** change the clean-URL rules from 200 rewrites to **301 redirects in the
other direction** — force `.html` → clean URL, so only one URL ever returns 200.

Suggested `_redirects` (replaces the clean-URL section):

```
# .html → clean URL (301, forced so it beats the static file)
/index.html               /                      301!
/about.html               /about                 301!
/services.html            /services              301!
/contact.html             /contact               301!
/resources.html           /resources             301!
/articles/index.html      /articles              301!
/articles/:slug.html      /articles/:slug        301!

# clean URL → file (200 rewrite, serves content)
/                         /index.html            200
/about                    /about.html            200
/services                 /services.html         200
/contact                  /contact.html          200
/resources                /resources.html        200
/articles                 /articles/index.html   200
/articles/                /articles/index.html   200
/articles/:slug           /articles/:slug.html   200
```

**Test this carefully — the ordering interacts.** Netlify processes rules top-down
and the `!` force flag makes a rule win over an existing static file. There is a
real risk of a redirect loop if the two directions fight. Verify every URL form
with `curl -I` before deploying, and test on the `.netlify.app` subdomain first.

### Hypothesis 2 — `/articles` vs `/articles/` trailing slash

The sitemap lists `https://northpeakfp.com/articles` (no trailing slash). The
current `_redirects` only has a rule for `/articles/` **with** the slash. Netlify
may be 301-ing `/articles` → `/articles/`, which Search Console reports as
*"Page with redirect"* for a URL that's in the sitemap — a legitimate warning.

**Fix:** included above (explicit rule for both forms).

### Hypothesis 3 — legacy `www` URLs from the first sitemap

The **first** sitemap submitted to Google contained `https://www.northpeakfp.com/...`
URLs. That was a bug I found and fixed, but Google may have crawled the bad version
first. Those www URLs now 301 to apex → *"Page with redirect."*

**This one resolves itself.** No action needed beyond confirming the current
sitemap is the apex version (it is).

### Hypothesis 4 — cached 403s from when the site was private

The Netlify project defaulted to **private visibility** for roughly the first day.
Google may have attempted crawls during that window and cached failures. The
sitemap showed "Couldn't fetch" for exactly this reason.

**Fix:** in Search Console, use **Validate Fix** on any affected group after
Hypothesis 1 is deployed. That prompts a recrawl.

### Hypothesis 5 — genuinely not-yet-indexed

Some pages will legitimately show *"Discovered – currently not indexed"* or
*"Crawled – currently not indexed."* On a new site with no backlinks this is normal
and not fixable by code. It resolves with age, links, and Google Business Profile.
**Do not burn time trying to force these.**

### Suggested working order

1. Pull the actual GSC **Pages** report and bucket the errors by reason.
2. Fix Hypothesis 1 and 2 in `_redirects`; verify with `curl -I` on every URL form.
3. Redeploy; re-verify.
4. Resubmit sitemap; click **Validate Fix** on affected groups.
5. Wait 1–2 weeks before judging. Resubmitting repeatedly does nothing.

### One more thing worth auditing

`PUBDATE = "2026-07-29"` is hardcoded and applied to all 25 articles as both
`datePublished` and `dateModified`. Identical dates across every article is a weak
signal and slightly dishonest once articles get edited. Consider per-article dates.

## 10. Landmines — things that will bite you

1. **Netlify deploy root.** Netlify serves whatever folder you drop **as the site
   root**. It needs `index.html` at the top level. Dropping the parent folder
   produces "Page Not Found." This already happened once. Use
   `DEPLOY-THIS-northpeak-site.zip` (index.html at zip root) or drag the
   `northpeak-site` folder itself.

2. **Netlify project visibility defaults to Private** on this account/team. A newly
   created project will return **403 to everyone including Googlebot**. Setting:
   Project configuration → **General → Visitor access → Project visibility** →
   Public. (It is *not* under "Access & security" — Netlify renamed it. Also check
   the team-level default so new projects don't inherit Private.)

3. **The DNS email records.** Repeating because it's the only irreversible risk.
   MX, SPF, DKIM stay untouched. Test with a real email after any DNS change.

4. **Squarespace DNS labels the value field differently per record type** — "Data"
   for A/MX, "Text" for TXT. Same field.

5. **The `.html` files still exist** even though canonicals point at clean URLs.
   That's Hypothesis 1 in §7.

6. **Article titles over 60 characters** must get an entry in `SEO_TITLES` or the
   `<title>` blows past Google's display limit. The validation script catches this.

7. **`og-image.jpg` was once referenced but missing** — every share previewed as a
   blank box. It exists now. If you change the site structure, verify it still does.

8. **The container/workspace resets.** All source lives in the delivered zips.
   Extract `northpeak-complete-package.zip` to get both the site and the generators.
